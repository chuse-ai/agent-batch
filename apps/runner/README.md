# runner

A Node process that connects out to the hub and runs many jobs' agents at once. It runs on its user's Node, from 22.19, so it uses only what Node 22 has. It runs separately from the CLI, which calls the hub over HTTP. After `vp pack`, `vp run start` starts a Runner from the environment:

- `HUB_URL`: the hub's URL.
- `RUNNER_REGISTRATION_KEY`: an API key granted `runner: ["register"]`, shared by Runners. A Runner uses it on its first start to register and receive a key of its own.
- `RUNNER_MODEL_PROVIDER` and `RUNNER_MODEL_ID`: the model every job runs on, as Pi names it, such as `anthropic` and `claude-sonnet-5-5`. The provider's key is read from the environment, as Pi reads it (for example `ANTHROPIC_API_KEY`), or the Runner uses its sign-in to the provider's subscription (see below). The Runner refuses to start when Pi does not know the model, finds neither a key nor a sign-in for its provider, or cannot renew the sign-in; in the first two cases it lists the models it has a key or sign-in for.
- `RUNNER_THINKING_LEVEL`: how hard the model thinks, one of Pi's levels from `off` to `max`; `medium` by default, as in Pi's coding agent.
- `RUNNER_DATA_DIR`: where the Runner keeps its own key, its jobs' journals and Workspaces, and anything else that must survive restarts; `data` by default.
- `RUNNER_MAX_JOBS`: how many jobs the Runner runs at once; 8 by default.
- `RUNNER_JOB_MEMORY_LIMIT`: how much memory each job's processes may use together, in systemd's notation; `1G` by default. A command that goes over is stopped and the agent is told.
- `RUNNER_JOB_READ_PATHS`: folders jobs may read besides the system's, separated by `:` as in `PATH`, such as where mise, nvm or Homebrew keep the tools jobs should use.
- `RUNNER_RUN_WITHOUT_SANDBOX`: `true` runs jobs without a sandbox where none can start, instead of refusing to start; only for jobs whose inputs you trust.

A Runner can run its jobs on a subscription instead of a key, such as a ChatGPT plan with Sign in with ChatGPT (provider `openai`, for example model `gpt-6-luna`). `vp run start login` signs in to `RUNNER_MODEL_PROVIDER`: it prints a page to open in a browser on any device, and on a host without a browser the page ends on an address on `127.0.0.1` that does not load; paste that address back into the command. The sign-in is saved in `auth.json` in `RUNNER_DATA_DIR`, readable only by the Runner's user and out of jobs' reach, and Pi renews it as it expires. A Runner already running uses a new sign-in from its next model call. A sign-in takes the place of the provider's key in the environment; to use the key again, stop the Runner, delete `auth.json` and start it again, as a Runner renewing the sign-in would save it again. A sign-in is one person's: run only that person's own jobs on it, on a host only they control, within their plan's usage limits; once the plan's limit is reached, model calls fail and so do the jobs that make them. Each host signs in itself, as a copied `auth.json` would be renewed by two hosts, and the second renewal fails. In the image, run `node dist/main.mjs login` in a container with the Runner's volume, for example `docker run --rm -it --volume runner-data:/data --env RUNNER_MODEL_PROVIDER=openai ghcr.io/chuse-ai/agent-batch-runner node dist/main.mjs login`. Whether a provider's terms allow running jobs on its subscription is for the person signing in to check, and they do so at their own risk; for ChatGPT, see OpenAI's [terms and policies](https://openai.com/policies) and its guide to [Sign in with ChatGPT](https://developers.openai.com/siwc/token-sharing-open-source).

Once connected, the Runner says hello and syncs with the hub: it offers its free slots, the hub places queued jobs on them, and the Runner reports what becomes of each job. It reports its jobs' new events, usage and activity at the report interval the hub gives it, and at once when a job starts or ends. Once per sync interval it reports every job it holds, or syncs when it holds none to report, and it syncs when the hub hints that it has something new. Each job's agent runs on pi-durable, with a journal, a Workspace and a temp directory of its own: the job's Input files are in its `inputs/` folder, and the agent ends the job by submitting a result that matches the Result contract. The agent's file operations and commands run in an OS sandbox of the job's own: they read the system's programs and libraries, the folders in `RUNNER_JOB_READ_PATHS`, and the job's Workspace and temp directory, write only the last two, and have no network, no access to other jobs or the Runner's data, and none of the Runner's environment variables, so not the provider's key. Within its own folders a job may write anything, `.git/hooks` and `.git/config` included, so running git in a job's Workspace outside a sandbox runs what the job wrote there.

A Runner that stops, or is killed outright (by the out-of-memory killer, `kill -9` or a crash), recovers its jobs when it starts again on the same `RUNNER_DATA_DIR`: the hub sends it the jobs still placed on it, and each carries on from its journal where it left off, with its Workspace as it was. A tool call that had completed does not run again. One the stop cut off does not run again either: the job's commands stop with the Runner, and the agent gets pi-durable's `interrupted` result, saying the call may have partly run. A Runner that starts with fewer slots than the jobs placed on it, as after lowering `RUNNER_MAX_JOBS`, recovers as many as it has slots for, and the rest as those end. This covers the Runner's process, not the host: after a power loss or an operating-system crash, a job's last journal commits may be lost, and the job then carries on from slightly earlier.

## What a host needs

- **Linux**: `bwrap` (bubblewrap), `socat` and `rg` (ripgrep) on `PATH`, for example `sudo apt install bubblewrap socat ripgrep`. On Ubuntu 24.04, AppArmor strips the capabilities from the user namespaces that bubblewrap and sandbox-runtime's seccomp helper create, so the host needs `kernel.apparmor_restrict_unprivileged_userns=0` (`sudo sysctl -w`, and a file in `/etc/sysctl.d` to keep it), as sandbox-runtime documents. Ubuntu 25.04 and later also load a profile for bubblewrap, `bwrap-userns-restrict`, that denies capabilities to everything bubblewrap starts, the helper included, so there jobs cannot run in a sandbox until sandbox-runtime no longer needs one ([anthropics/sandbox-runtime#429](https://github.com/anthropics/sandbox-runtime/issues/429)); loading that profile on 24.04 does the same. The memory limit needs a user systemd manager of systemd 254 or later (Ubuntu 24.04, Debian 13): a desktop session has one; on a server, `loginctl enable-linger <user>` keeps one running for the Runner's user. Without it the Runner logs that jobs run without a memory limit.

- **macOS**: nothing to install; the sandbox is Seatbelt, and jobs run without a memory limit.
- **Windows**: run the Runner in WSL 2, as on Linux.
- **Docker**: the Runner's image, `ghcr.io/chuse-ai/agent-batch-runner`, runs as a non-root user and needs three options for its jobs' sandboxes, as BuildKit's rootless image does: Docker's defaults deny bubblewrap the namespaces it needs and mask the paths under `/proc` that a sandbox mounts its own over.

  ```sh
  docker run --security-opt seccomp=unconfined --security-opt systempaths=unconfined \
    --security-opt apparmor=unconfined --memory 8g --restart unless-stopped --volume runner-data:/data \
    --env HUB_URL --env RUNNER_REGISTRATION_KEY --env RUNNER_MODEL_PROVIDER --env RUNNER_MODEL_ID \
    --env ANTHROPIC_API_KEY ghcr.io/chuse-ai/agent-batch-runner
  ```

  `apparmor=unconfined` is needed only on hosts with AppArmor; on Ubuntu 24.04 the host also needs `kernel.apparmor_restrict_unprivileged_userns=0` (in `/etc/sysctl.d`), as BuildKit's rootless image does, and on Ubuntu 25.04 and later its jobs cannot run in a sandbox yet, as on the host. `--restart` starts the Runner again after it stops, as when it could not reach the hub on its first start. `RUNNER_DATA_DIR` is `/data` in the image, so keep it on a volume. A container has no user systemd, so jobs run without a memory limit of their own: `--memory` caps the Runner and its jobs together. Jobs' commands find the programs of Debian's slim image; for more, build an image from this one.

The Runner proves the sandbox works when it starts, and refuses to start, naming what is missing, if it does not.

A Runner the hub has removed, or a hub that no longer knows (for example after a reset), stops with a message instead of retrying; `vp run start register` discards its key and registers it again. Any other refusal, such as from a proxy or from a hub that cannot reach its database, is retried.

To remove a compromised host, delete its Runner on the hub (`DELETE /runners/{id}`), then revoke the registration key and create a new one for future hosts: the host still holds the old one and could otherwise register again. Runners already registered keep working, since they connect with their own keys. A registration key can also be created to expire (`expiresIn`), for a key meant for one batch of hosts.
