# The hub runs on Workers and in Docker alike, with Postgres and S3-compatible storage

> Implementation status: Both hub runtimes and Postgres are implemented. S3-compatible file/event storage, upload flows, compaction and retention described below are planned; events currently remain in Postgres.

The hub runs both on Cloudflare Workers and as a Docker image for Railway, a VPS, Kubernetes, or a company's own machine, and every feature lands on both. It is written to Web standards, with Durable Objects used only to hold runner connections on Workers. Its only database is Postgres, reached through Hyperdrive on Workers and directly elsewhere. Its tables live in their own schema, `agent_batch`, named in every statement, so the hub can share a database with other software; Hyperdrive resets `search_path` after each transaction, so the schema cannot be set once per connection. Files and jobs' events go to S3-compatible object storage, R2 by default; input files are uploaded straight to it through presigned URLs, while the small ones sent inline with a job stay in Postgres. Events land in Postgres as runners send them. The hub writes a job's events to object storage as JSON Lines when the job ends or is paused, or once its unwritten events pass a size limit, and then deletes those rows, so the database holds only the events not yet written, and object storage the rest.

## Considered options

- Workers first, with a Docker image later: whichever platform comes second falls further behind with every feature, and porting it grows with them.
- Docker only: the smallest test matrix, but the Workers hub, which holds runner connections in hibernating Durable Objects and needs no server of its own, would stop being maintained.
- D1: one SQLite database with a single writer, near its limits from the event stream at around a thousand concurrent jobs; billed per row written, so its cost grows with load; unavailable outside Cloudflare, so a Docker hub would need a second SQL dialect; and without interactive transactions.
- A Durable Object per job holding that job's events and state, with D1 as an index: scales furthest, but is billed per row and per request and exists only on Cloudflare.
- Supporting both SQLite (D1 or a file) and Postgres: a common pattern in self-hosted software, but a test matrix of two dialects across two runtimes before the first feature.
- Keeping all events in the database: tens of gigabytes a day at a thousand concurrent jobs.
- Writing each running job's events to object storage every 30 to 60 seconds: the database would hold only about a minute of each job's events, but a five-minute job would become five to ten objects, and S3, R2 and Google Cloud Storage charge for every write. An event is already safe once Postgres has committed it, so writing it to object storage sooner adds no safety. GitLab likewise buffers a running job's log and archives it to object storage when the job finishes.
- Runners uploading their jobs' events to object storage instead of sending them to the hub: the loss window would grow from one report to one upload. A Runner uploading a finished job's events as well, as GitHub Actions' runner uploads step logs, would spare the hub reading them back out of Postgres, but the hub would have to check the upload against what it stored and write the events itself when a Runner never uploads; it is left for deployments where that read is billed.
- A log or stream store on object storage, or Cloudflare's Pipelines: an extra service in every deployment, or one that exists only on Cloudflare; such stores fit better as optional destinations for the compacted chunks.

## Consequences

`agent-batch dev` runs Postgres locally next to the Docker setup the container backend already needs. The object layout is documented, so tools such as DuckDB can query jobs' events in place, and optional event sinks (OpenTelemetry export, analytics) can consume them once written. Postgres holds only the events not yet written, so its size follows how many jobs are running and how much each has produced, not how long the hub has run. A job's events are written as immutable segments, each uploaded before Postgres records it, and the rows it holds are deleted in the same transaction that records it, as Kafka's and Pulsar's tiered storage upload a segment before publishing it and deleting the local copy: a crash then leaves at most an object nothing refers to, which a periodic sweep deletes, and a retried segment must match the one already written, as PostgreSQL requires of its WAL archives. The size limit does not cap the database while object storage is unreachable, so the age of the oldest unwritten event is monitored. The hub acknowledges events once Postgres commits them, so a Postgres that fails over to an asynchronously replicated standby can lose acknowledged events: PostgreSQL's replication is asynchronous by default, and on failover "some transactions that were committed may not have been replicated". The hub then reports an earlier position, and the Runner sends those events again from the job's Pi journal, which works while the job's host still holds it; once the host is gone, they are lost. A deployment that must lose none runs synchronous replication. A Docker hub accepts runner connections with crossws instead of Durable Objects, because its upgrade hook answers a refused runner with the hub's full response, which Hono's Node helper reduces to an empty body, and serves the protocol through oRPC's crossws handler. It runs as a single process: a second would hold its own share of runner connections, which the first could not reach to close a removed runner's socket or send it commands. Running several needs those messages routed between processes, for example with Postgres's `LISTEN` and `NOTIFY`, which a direct connection supports and Hyperdrive does not. So Durable Objects only hold connections (sockets, alarms, hibernation); what the hub records and decides about runners and jobs lives in modules that use no Cloudflare APIs, and a Docker hub replaces only the connection layer. If load ever outgrows one Postgres database, the per-job event store can move to Durable Objects behind the same interface. The same integration suite runs against both hubs (ADR 0003), and what differs between them is a service with one Layer per platform (ADR 0022).
