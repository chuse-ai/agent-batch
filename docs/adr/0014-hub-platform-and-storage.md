# The hub runs on Workers and in Docker alike, with Postgres

The hub runs both on Cloudflare Workers and as a Docker image for Railway, a VPS, Kubernetes, or a company's own machine, and every feature lands on both. It is written to Web standards, with Durable Objects used only to hold runner connections on Workers. Its only database is Postgres, reached through Hyperdrive on Workers and directly elsewhere. Its tables live in their own schema, `agent_batch`, named in every statement, so the hub can share a database with other software; Hyperdrive resets `search_path` after each transaction, so the schema cannot be set once per connection. Jobs' events land in Postgres as runners send them.

## Considered options

- Workers first, with a Docker image later: whichever platform comes second falls further behind with every feature, and porting it grows with them.
- Docker only: the smallest test matrix, but the Workers hub, which holds runner connections in hibernating Durable Objects and needs no server of its own, would stop being maintained.
- D1: one SQLite database with a single writer, near its limits from the event stream at around a thousand concurrent jobs; billed per row written, so its cost grows with load; unavailable outside Cloudflare, so a Docker hub would need a second SQL dialect; and without interactive transactions.
- A Durable Object per job holding that job's events and state, with D1 as an index: scales furthest, but is billed per row and per request and exists only on Cloudflare.
- Supporting both SQLite (D1 or a file) and Postgres: a common pattern in self-hosted software, but a test matrix of two dialects across two runtimes before the first feature.

## Consequences

The hub acknowledges events once Postgres commits them, so a Postgres that fails over to an asynchronously replicated standby can lose acknowledged events: PostgreSQL's replication is asynchronous by default, and on failover "some transactions that were committed may not have been replicated". The hub then reports an earlier position, and the Runner sends those events again from the job's Pi journal, which works while the job's host still holds it; once the host is gone, they are lost. A deployment that must lose none runs synchronous replication. A Docker hub accepts runner connections with crossws instead of Durable Objects, because its upgrade hook answers a refused runner with the hub's full response, which Hono's Node helper reduces to an empty body, and serves the protocol through oRPC's crossws handler. It runs as a single process: a second would hold its own share of runner connections, which the first could not reach to close a removed runner's socket or send it commands. Running several needs those messages routed between processes, for example with Postgres's `LISTEN` and `NOTIFY`, which a direct connection supports and Hyperdrive does not. So Durable Objects only hold connections (sockets, alarms, hibernation); what the hub records and decides about runners and jobs lives in modules that use no Cloudflare APIs, and a Docker hub replaces only the connection layer. If load ever outgrows one Postgres database, the per-job event store can move to Durable Objects behind the same interface. The same integration suite runs against both hubs (ADR 0003), and what differs between them is a service with one Layer per platform (ADR 0022).
