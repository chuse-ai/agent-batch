# Better Auth provides members, sign-in and API keys

The hub's identities come from Better Auth on the hub's Postgres, in the hub's schema. Members sign in with an email and password or through the organization's identity provider (OIDC first, SAML later), and a deployment can turn passwords off once SSO is in place; the CLI signs in with a device login. Services and runners use organization-owned API keys that are named, carry permissions and are revocable. Only signed-in admins and owners manage keys, because Better Auth lists and deletes keys for a member's session, so no key can reach member operations. Every job records who submitted it. Better Auth's organization, API key, SSO and device authorization plugins cover these needs without authentication code of our own.

The Organization and its owner are created from environment variables (`ADMIN_EMAIL` and `ADMIN_PASSWORD`) while no Organization exists, and the variables are ignored afterwards, as Grafana, Authentik and Keycloak treat theirs: on Docker when the hub starts, on Workers as a deploy step beside migrations. Without an Organization or the variables, setting up fails and says what to set. Better Auth cannot create the owner and the Organization in one transaction, so setup stopped between the two leaves the owner without an Organization, and setting up again reuses the owner. A forgotten password is reset with a command run with database access, as with Grafana's `grafana cli admin reset-admin-password` and GitLab's `gitlab:password:reset`, since database access is what only those running the hub have. Once passwords can be turned off, recovery also needs a temporary admin who signs in without the identity provider, as Keycloak's `bootstrap-admin` creates, since a broken provider would otherwise lock every member out.

Better Auth runs inside the Workers hub with a fresh instance per request and its runtime schema check off. better-auth/better-auth#10315 and better-auth/better-auth#11651 describe auth calls hanging in a Workers isolate after a cancelled request leaves a promise shared across requests unsettled; 1.7.8 fixes the module-level part, and instances built per request avoid the rest. Rate-limit counts are kept in the database, so they hold across hub replicas and Workers isolates, and the header carrying the client's address is a deployment setting, because a proxy that rewrites `X-Forwarded-For` puts every client into one bucket.

## Considered options

- Writing our own token handling: small at first, but members, SSO, scoped keys and device login together are a large, security-sensitive subsystem.
- Cloudflare Access in front of the hub: it cannot protect a hub on localhost or outside Cloudflare, so it stays an optional outer layer for deployments that want it.
- Sign-in through an identity provider only, as Tailscale does: small teams and local development often have no provider, and self-hosted tools such as Grafana and GitLab offer passwords with a switch to turn them off.
- Setting up in the browser on the first visit, as n8n and Metabase do: it needs the dashboard, which brings it later; until then, environment variables are the only way to set up a hub without a UI, and they remain the way for automated deploys.
- Environment variables that set the owner on every start (n8n's opt-in mode): rare, and it makes the environment a second source of truth for a member managed in the hub.

## Consequences

Better Auth's tables share the hub's schema and naming (ADR 0020); its CLI drafts them into hand-written migrations. `better-auth` and `@better-auth/api-key` are pinned to one version together, and every upgrade re-runs the draft. Better Auth signs members in only from the hub's own origin once a request carries browser fetch metadata, as Node's `fetch` does, so the dashboard is served from the hub's origin. Better Auth answers a key lacking a permission as it answers an unknown key, with 401, so the answer reveals nothing about the key. Every route of Better Auth and its plugins is served under `/api/auth/*`, so the hub turns off those for what it wraps with rules of its own (API keys) and Organization deletion, and adding a plugin includes reviewing the routes it brings. Better Auth records no creator for organization-owned keys, and its audit logs come only with its paid hosted service; the hub records who did what in its own data, starting when a feature needs it, such as jobs recording who submitted them.
