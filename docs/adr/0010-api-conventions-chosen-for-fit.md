# API conventions are chosen for fit, in camelCase

The API uses camelCase for field names and for string values (`customId`, `outputContract`, `runTimedOut`), with lowercase, plural, hyphenated URL paths (`/jobs/:id`, `/api-keys`). Cloudflare Workflows, the platform service closest to ours, does the same in its JavaScript API, including state values such as `waitingForPause`. Several of our surfaces are camelCase whatever we choose (JavaScript callers, the JSON Schema keywords inside output contracts, data from Pi), so camelCase is the only casing that can be the same everywhere. Agent tool names are the exception: they follow the snake_case convention models are trained on (`submit_output`).

Patterns are chosen for how well they fit what we need, not by the project they come from: a less common design that works better wins over the most familiar one. Names inside our code and our domain terms are our own, chosen for clarity.

A single resource is returned bare. A list is returned in pages, each a page object whose items are named for what they hold. A job's events are read by position: `after` takes a position, the ID of the last event the caller has, and `limit` (1 to 100) caps the page, which also stops after about 1 MiB of events but always holds one if there is any. The page says `hasMore` when more is already stored, so the caller asks again at once, and carries the job's `status`, read with its events, so a caller polling a running job learns that it ended from the same page, without a second request that could miss events stored in between. A status rather than a `done` flag: once a stopped job can be carried on, `done` would promise more than it can. Redis Streams' `XREAD`, CouchDB's changes feed and the browser's `Last-Event-ID` likewise read on from a position the reader keeps.

A list of jobs is read newest first, the same way: `after` takes the ID of the last job the caller has, and the page holds the jobs created before it, `limit` of them (1 to 100, 50 by default), saying `hasMore` when there are more, as Stripe's `starting_after` takes an object's ID. Job IDs are UUIDv7s, ordered by when they were made, so the ID alone orders the list, and a page stays correct when the job it starts after is deleted or new jobs come meanwhile; those show on a new first page. Filters, such as a label or a status, narrow the list without changing its order.

Every HTTP input the hub takes, the public API's and the Runner protocol's alike (ADR 0026), is checked strictly, in its body and in a read's query string: a parameter the call does not define, such as one renamed or misspelled, is refused with 400 naming it and its path. Ignoring it would run the request as if it were absent, such as a job without the files its caller meant to give it, or a list without the filter its caller misspelled, answering with every job. Refusing it also keeps the name free for a parameter added later, which an old caller's stray one would otherwise collide with. Microsoft's Azure REST API guidelines fail a request with any JSON field the service does not understand, Zalando's guidelines have servers answer 400 to unknown input fields in the payload or URL, the Anthropic and OpenAI APIs refuse unknown fields in a request body, and Anthropic's Compliance API refuses a query parameter its endpoint does not define, rather than ignoring it. Answers are not checked that way, so the hub can add fields to them without breaking a caller that validates them; nor are the upload's headers, which carry far more than the API reads.

Some input goes unchecked, as oRPC builds a call's input from the request. A write's query string never reaches its schema, except the upload's, `PUT /blobs/{digest}`, which reaches its input and is dropped there unchecked; nor does the query string of a read without input, `GET /runners` and `GET /api-keys`. None of these calls takes query parameters, so nothing a caller means can be dropped there. A body that is not an object, on a call with path parameters, is taken as no body, so an array sent to `POST /jobs/{id}/resume`, whose fields are all optional, resumes the job with its defaults. The hub refuses unknown fields in every body, but the OpenAPI document leaves `additionalProperties: false` off the body of a call with path parameters, a regression in oRPC 2 (middleapi/orpc#2360).

## Considered options

snake_case field names, as in Cloudflare's account-level REST API, Wrangler configuration, and the OpenAI and Anthropic APIs, would look familiar to some callers, but the same job would then be snake_case over HTTP and camelCase in JavaScript, with camelCase schema keywords nested inside snake_case fields. Our callers send jobs, not model requests, so they gain little from matching the model APIs.

An opaque cursor the hub mints, as Google's AIP-158 `page_token` is, would hold only the job ID `after` already takes, and would need a rule for a request whose filters differ from those the cursor was minted with. A later sort order, such as by when a job ended, would need a position the ID alone cannot give; a cursor for that order would then come beside `after`.

Unknown parameters could be dropped silently, as Zod's `z.object` does by default, so a hub would accept a request from a caller newer than itself. But a misspelled or renamed parameter would then run the request as if it were absent, and the caller would learn of it only from a wrong result, if at all. Accepting them with a warning, as Kubernetes's `fieldValidation=Warn` does, still runs that request and tells only a caller that reads warnings, which a program submitting jobs rarely does. Refusing them should be reconsidered if callers commonly run against hubs older than themselves, which would then refuse the parameters added since; a caller could leave out what its hub does not know, or a request could ask for unknown parameters to be ignored.
