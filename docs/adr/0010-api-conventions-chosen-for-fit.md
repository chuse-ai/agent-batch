# API conventions are chosen for fit, in camelCase

Every surface of the API (the HTTP API, the TypeScript client, and a Workers service binding) uses camelCase for field names and for string values (`idempotencyKey`, `resultContract`, `deadlineExceeded`), with lowercase, plural, hyphenated URL paths (`/jobs/:id`, `/api-keys`). Cloudflare Workflows, the platform service closest to ours, does the same in its JavaScript API, including state values such as `waitingForPause`. Several of our surfaces are camelCase whatever we choose (JavaScript bindings, the JSON Schema keywords inside result contracts, data from Pi), so camelCase is the only casing that can be the same everywhere. Agent tool names are the exception: they follow the snake_case convention models are trained on (`submit_result`).

Patterns are chosen for how well they fit what we need, not by the project they come from: a less common design that works better wins over the most familiar one. Names inside our code and our domain terms are our own, chosen for clarity.

A single resource is returned bare. A list is returned in pages, each a page object whose items are named for what they hold. A job's events are read by position: `after` takes a position, the ID of the last event the caller has, and `limit` (1 to 100) caps the page, which also stops after about 1 MiB of events but always holds one if there is any. The page says `hasMore` when more is already stored, so the caller asks again at once, and carries the job's `status`, read with its events, so a caller polling a running job learns that it ended from the same page, without a second request that could miss events stored in between. A status rather than a `done` flag: once a stopped job can be carried on, `done` would promise more than it can. Redis Streams' `XREAD`, CouchDB's changes feed and the browser's `Last-Event-ID` likewise read on from a position the reader keeps. Collections such as jobs will be listed with an opaque cursor instead, which can carry their filters and order as Google's AIP-158 sets out; a bare ID cannot.

## Considered options

snake_case field names, as in Cloudflare's account-level REST API, Wrangler configuration, and the OpenAI and Anthropic APIs, would look familiar to some callers, but the same job would then be snake_case over HTTP and camelCase in a service binding, with camelCase schema keywords nested inside snake_case fields. Our callers send jobs, not model requests, so they gain little from matching the model APIs.
