# MikroORM for data access, with typed Kysely for hot paths

The hub defines its schema as MikroORM 7 entities (`defineEntity`), generates migrations from them, and reads and writes through MikroORM's entity manager by default. Performance-critical and complex queries use the Kysely builder that MikroORM exposes (`em.getKysely()`), typed from the same entities. MikroORM supplies what plain Kysely leaves to conventions (column naming, write semantics, per-property type conversion, loading relations) while keeping SQL-level control where it matters.

On Workers, MikroORM must use functions pre-generated by `mikro-orm compile`, because workerd forbids `new Function`; the generated file is regenerated whenever entities change. Creating a MikroORM instance runs entity discovery, which takes longer with every entity (measured locally in workerd: about 1 ms with one entity, 6 ms with 60, 10 ms with 100), while forking an entity manager takes a few microseconds. So the hub creates one instance on its first request, keeps it for the isolate, and forks an entity manager per request. Workers forbid using a connection outside the request that opened it, so `pg`'s pool keeps none: `maxUses: 1` closes each connection when it is released, and an unbounded `max` stops requests from waiting for each other's connections; Hyperdrive pools the real connections to Postgres. Nothing can be prepared at module scope, because workerd forbids the random values and timers MikroORM uses during setup.

## Considered options

- Kysely alone, with kysely-ctl migrations and kysely-codegen types: lighter and the fallback, but migrations are written by hand, types are generated from a live database, and type conversion is configured separately from typing.
- Drizzle schema with Kysely typed through Drizzle's bridge: the bridge is gone from Drizzle 1.0.
- ZenStack: a separate schema language and a Prisma-style API, further from Kysely.

## Consequences

Lazy loading is avoided in hot paths (relations are populated explicitly), and each request uses its own forked entity manager. A fresh isolate's first request pays MikroORM's setup once. Reusing the instance relies on MikroORM holding one Kysely client per instance and passing `driverOptions` to `pg`'s pool, which its documentation does not describe for this use, so it is re-checked on every MikroORM upgrade; the hub's tests fail if a connection is reused across requests. If the ORM outgrows the Workers free plan, the entities and database stay as they are and the entity-manager calls move to Kysely.

So far the hub relies on MikroORM mainly for its schema in code: migrations generated from the entities, and Kysely types derived from them. Its unit of work, identity map, version-based optimistic locking and relation loading suit models that are loaded, edited and saved; the hub's writes are mostly conditional statements (change a row only if it is still in the expected state or still owned by the caller), which read most clearly as single `UPDATE … WHERE` statements, and its reads are mostly flat lists and aggregates. If that stays true, the hub could keep the entities and generated migrations and run plain Kysely at runtime, typed from the entities through MikroORM's `InferKyselyDB`; whether that type works with `defineEntity` and keeps MikroORM out of the Worker bundle is not yet verified.
