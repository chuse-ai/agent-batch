# The hub is the only address; each runner holds a WebSocket to it

_The protocol on the socket, its subscription and the alarm are replaced by ADR 0026; the addressing, identity and heartbeat below stand._

Callers and runners connect only to the hub, and hosts are never reachable from outside. Each runner on a host opens one WebSocket to the hub and keeps it open, reopening it when it drops. The runner protocol is typed oRPC over that socket: the runner subscribes to the hub's commands (new work, pause, cancel, resume), which also registers it, subscribes again whenever that stream ends, and calls the hub to send event batches. On the hub, one Durable Object per runner holds the socket with Cloudflare's hibernation API and oRPC's hibernation plugin, so the subscription survives while the object sleeps. Every 30 seconds the runner sends a heartbeat, a `ping` text message that the runtime answers with `pong` without waking the object; the object's alarm is set for three intervals after the last heartbeat, and when it fires, records that heartbeat as when the runner was last seen and drops the runner's sockets if no newer one arrived. The hub keeps no online state, only when it last saw each runner; every write can only move that time forward, so writes arriving late, twice or out of order cannot make it wrong. A runner whose heartbeats go unanswered as long starts a new connection. The hub stores results and jobs' events and serves them to callers, so polling, inspecting a running job, and later steering it and passing messages between jobs all go through one place.

A runner starts with an API key shared by many runners and registers once, receiving a key of its own that it keeps in its data directory and connects with, as GitHub Actions and Buildkite runners register. The hub takes a runner's identity from that key, so one runner cannot connect as another, and a restarted runner keeps its identity. Runners the hub launches in the cloud receive their own key when launched. The shared key is long-lived and revocable, as Buildkite's agent tokens are, so new hosts can join with one setting; removing a compromised host therefore includes replacing the shared key, which leaves registered runners working. Removing a runner deletes its own key, and the database deletes the runner's record with it. The hub answers a key it does not know with a code saying so, and a runner stops only on that answer, as a GitHub Actions runner stops only on its server's `invalid_client`; any other refusal, from a proxy or from a hub that cannot reach its database, is retried.

We considered the opposite: the hub assigns a runner and returns its address, and callers then talk to that runner directly, keeping long-lived traffic off a central service. We rejected it because company hosts sit behind NAT and firewalls, so every host would have to be made reachable; every runner would have to check identities and keep its own audit trail; a dead host would take finished results with it; and jobs on different hosts could not reach each other at all. A hub that everyone connects out to solves all four.

We also considered runners polling the hub over plain HTTPS. It needs no object per connection, but idle runners keep making requests (three runners polling every two seconds exceed the Workers free plan's 100,000 requests a day), commands wait for the next poll, and every event batch is a full request where a socket message is billed at a twentieth of one. On a hub running on its own server the two cost about the same: an idle socket held with `ws` takes about 14 KB, and polling a request and a query per interval. The runners that do poll, such as GitLab's and GitHub Actions', talk to server fleets billed for CPU rather than per request, and GitLab recommends long polling once many runners poll. PartyServer was considered for holding the sockets; oRPC's WebSocket adapters keep the protocol in the same typed contract as the HTTP API and also run on Node. The heartbeat is our own because nothing below provides one: Cloudflare closes idle WebSockets and recommends a client-side heartbeat, Workers WebSockets cannot send protocol pings, the hub's runtime answers and records only a text message without waking the hub, and neither oRPC nor partysocket sends heartbeats or notices a silent peer.

## Consequences

The runner remains the source of truth for executing a job: pi-durable's state and the workspace stay on its host, and a job carries on there, recovered after a restart or resumed after a pause. A running job is not moved to another host, since carrying it on elsewhere would need its workspace as well as pi's state. The hub keeps every event of a job and its results, forwarded as they happen, so a job can be inspected at any time, including after its host has gone away; retention bounds what this stores.

Every runner dials the hub by URL, so opening a socket has a time limit, 4 seconds as partysocket's connection timeout, and it bounds only the attempt to open the socket: a limit attached to the upgrade request itself also closes the open socket when it fires. Reconnecting follows partysocket's other defaults too: the delay grows from about 3 to 10 seconds, and only a connection that stayed open for 5 seconds starts it over, so a hub that accepts and then drops runners is not redialled at a fixed pace. Each delay varies by up to a fifth either way, as gRPC's connection backoff specifies, so runners dropped together, as when a hub restarts, do not redial together; partysocket varies only its first delay, once per process. partysocket itself does not fit, because it reconnects underneath by itself, while oRPC's WebSocket link treats each close as the end of that connection. A runner needs a network that lets WebSockets through to the hub. Socket.IO, SignalR and Buildkite's agent fall back to polling where proxies block WebSockets; runners have no such fallback until a network needs one. Pushing live updates to people watching a job is designed with the dashboard. If a heavy stream ever needs to bypass the hub, the hub can hand the client a short-lived direct address to the runner; the client hides this, so the API does not change.
