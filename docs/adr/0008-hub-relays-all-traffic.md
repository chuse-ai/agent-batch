# The hub is the only address; each runner holds a WebSocket to it

Callers and runners connect only to the hub, and hosts are never reachable from outside. Each runner on a host opens one WebSocket to the hub and keeps it open, reopening it when it drops. The runner protocol is typed oRPC over that socket: the runner subscribes to the hub's commands (new work, pause, cancel, resume), which also registers it, subscribes again whenever that stream ends, and calls the hub to send event batches. On the hub, one Durable Object per runner holds the socket with Cloudflare's hibernation API and oRPC's hibernation plugin, so the subscription survives while the object sleeps. Every 30 seconds the runner sends a heartbeat, a `ping` text message that the runtime answers with `pong` without waking the object; the object's alarm is set for three intervals after the last heartbeat, and when it fires, records that heartbeat as when the runner was last seen and drops the runner's sockets if no newer one arrived. The hub keeps no online state, only when it last saw each runner; every write can only move that time forward, so writes arriving late, twice or out of order cannot make it wrong. A runner whose heartbeats go unanswered as long starts a new connection. The hub stores results and the event history and serves them to callers, so polling, inspecting a running job, and later steering it and passing messages between jobs all go through one place.

We considered the opposite: the hub assigns a runner and returns its address, and callers then talk to that runner directly, keeping long-lived traffic off a central service. We rejected it because company hosts sit behind NAT and firewalls, so every host would have to be made reachable; every runner would have to check identities and keep its own audit trail; a dead host would take finished results with it; and jobs on different hosts could not reach each other at all. A hub that everyone connects out to solves all four.

We also considered runners polling the hub over plain HTTPS. It needs no object per connection, but idle runners keep making requests (three runners polling every two seconds exceed the Workers free plan's 100,000 requests a day), commands wait for the next poll, and every event batch is a full request where a socket message is billed at a twentieth of one. PartyServer was considered for holding the sockets; oRPC's WebSocket adapters keep the protocol in the same typed contract as the HTTP API and also run on Node. The heartbeat is our own because nothing below provides one: Cloudflare closes idle WebSockets and recommends a client-side heartbeat, Workers WebSockets cannot send protocol pings, and neither oRPC nor partysocket sends heartbeats or notices a silent peer.

## Consequences

The runner remains the source of truth for executing a job: pi-durable's state and the workspace stay on its host, and resuming happens there. The hub keeps the complete event history and the results, forwarded as they happen, so a job can be inspected at any time, including after its host has gone away; retention bounds what this stores.

A runner on Cloudflare is reached through a service binding rather than holding an idle client socket, which cannot hibernate. Opening a socket over a service binding needs no time limit: the call stays inside Cloudflare and fails rather than hangs. A runner that dials the hub by URL (a runner on a host, or any runner when the hub runs outside Workers) needs one, bounding only the attempt to open the socket, as partysocket's connection timeout does; a limit attached to the upgrade request itself also closes the open socket when it fires. Pushing live updates to people watching a job is designed with the dashboard. If a heavy stream ever needs to bypass the hub, the hub can hand the client a short-lived direct address to the runner; the client hides this, so the API does not change.
