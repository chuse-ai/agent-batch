# Effect structures the hub's and runners' own logic

The hub and runners write their own logic with Effect 4: a runner's job lifecycle (one supervised scope per job, retries with backoff, timeouts per attempt and per job, cancellation passed to pi-durable, and shutdown that stops taking jobs, interrupts them, flushes events and closes resources within a deadline), and the hub's placement and request handling. What differs between platforms is a service with one Layer per platform, such as runner connections. The database and Better Auth on it differ only in how long they live, so one Layer builds them on both: per request on Workers, through Hyperdrive, and once in a Docker hub. Timers are not a service of their own yet: their only user, the heartbeat check, is scheduled inside each platform's runner connections (Durable Object alarms on Workers, fibers in a Docker hub, ADR 0014) while the decision it makes is shared; a second user, such as job deadlines, would make them one. The libraries already chosen stay: Hono and oRPC, with handlers written as Effects through oRPC's Effect adapter at the same version; Kysely with Kanel's types, each call wrapped in `Effect.tryPromise`, as Effect's migration guide recommends since its Kysely integration was removed in version 4; Zod for contracts; and Better Auth. Fibers do not survive a restart, so pi-durable recovers jobs.

Effect 4 is a long-term support release with at least three years of fixes. Modules tagged `@stability unstable` or `experimental`, such as its WebSocket and Node runtime, are used where they fit and followed through their changes on upgrade. Effect's own HTTP, RPC, SQL, Schema and workflow modules are not: they would replace libraries chosen for reasons of their own, such as Kysely checking queries against the database's types at compile time (ADR 0020). On Workers nothing outlives a request: runtimes and resources are scoped to the request or the Durable Object.

## Considered options

- Effect throughout, with its HTTP API, RPC, SQL and Schema modules: they replace established libraries, and Effect's SQL types results by schemas checked at runtime rather than by the compiler against the database.
- Effect only for retry policies, as OpenStatus records in its ADR: supervision, cancellation and shutdown would stay hand-written across many places.
- No Effect: p-retry, `AbortSignal` composition, neverthrow and plain interfaces each cover a piece; combining them into supervision with typed errors and testable time is what Effect provides.
- Runners only: a Docker hub is a long-running process with the same needs for shutdown, timers and resource cleanup, and the platform seam is the same problem.

## Consequences

The oRPC adapter, an experimental package, takes the same version as oRPC. Tests that run an Effect directly use `@effect/vitest`, which needs Vitest 5, as Vite+ provides, and its test clock lets timing logic run without waiting; the clock reaches only the test's own fibers, so tests through a promise facade, such as `startRunner()`, run on real time. A Worker grows by about 30 to 37 KB gzipped. The shared contract package stays plain TypeScript with Zod, so clients need no Effect. Contributors learn Effect's model: lazy effects, typed failures and defects, scopes and Layers.
