# The runner protocol is JSON-RPC over the socket, driven by the Runner

A Runner's socket to the hub (ADR 0008) carries JSON-RPC 2.0, one object per text message, framed and dispatched with `json-rpc-2.0` and typed by Zod Mini schemas for each method's params, result and refusal data in the `contract` package; oRPC stays for the HTTP API. The protocol version is the WebSocket subprotocol, `agent-batch.v1`: a Runner offers the versions it speaks, newest first, and a hub that supports none of them refuses the upgrade with a 400 and a Problem Details body (ADR 0023) naming the versions it supports, which the Runner's client can read, so it logs what to upgrade and retries with its usual backoff. Within a version only fields are added, and a receiver ignores fields it does not know, as Zod's objects do by default; a new method or a new value in a closed set bumps the version. Before 1.0 the hub supports one version at a time.

The Runner drives the exchange. It sends requests: a hello on connect, reports carrying the events of all its running jobs read from each job's pi-durable journal after the hub's position, and a sync about every three minutes with jitter, sooner when the hub hints or its capacity changes. The hub answers every one with the full desired state of all that Runner's jobs, new placements and the tombstones of purged jobs included. The hub itself sends only a notification, "sync now", with nothing in it; the one request it makes is a Workspace read, which it awaits only while the caller's own HTTP request keeps the Durable Object awake. So the hub holds nothing pending across hibernation and keeps no outbox: the journal is already a durable ordered log, entry IDs increase in commit order across all of a job's conversations, and the hub's position in it is one integer per job. Events are pi's entries unchanged, each naming its conversation, plus the hub's own entries; when a report carries the first entries of a conversation the hub has not seen, such as a sub-agent's, it carries that conversation's record too, with its parent and owner. A job's current activity is derived on the hub from the latest entries of every conversation of the job, not of its root alone.

Order is a placement generation plus forward-only intents within it: run, then pause or cancel, then purge; resuming a paused job is a new placement, so no revision counter exists, as Docker Swarm's task states only advance and serve as the clock. A Runner's work is scoped to its generation: nothing an old placement does can touch the next, which starts only after the old one is quiet, and a purged job leaves a tombstone so a late placement cannot revive it. A report says, per job, the placement, the intent applied and the actual outcome, so a caller sees the current intent, the last confirmed outcome and whether they agree; a job that finished before its cancel arrived is reported as finished. Each sync or report also refreshes when the Runner was last seen, written at most every three minutes; a Runner silent for about seven minutes counts as gone. The text ping and pong of ADR 0008 stay as transport health and are answered without waking the object; its alarm goes. The socket's own `permessage-deflate` compresses the traffic, negotiated by Workers already and enabled on the Node hub through crossws; nothing in the protocol compresses. The library's error mapping is replaced so that a thrown message never reaches the Runner: refusals are application codes with a stable `data.reason`, anything unexpected is a plain internal error.

## Considered options

- oRPC on the socket, as ADR 0008 had it: its WebSocket adapters carry oRPC's own framing, which changed between majors, so a Runner on one major could not talk to a hub on the next, and we are on a pre-release major. The socket needs a wire format whose versioning we control; JSON-RPC 2.0 has been frozen since 2010 and carries LSP and MCP over long-lived peer connections.
- Effect's `rpc` module with its JSON-RPC serialization: tagged unstable (ADR 0022), and it puts Effect-specific messages and error shapes on the wire, serves one direction only, and keeps state per client on the server.
- `vscode-jsonrpc`: runs in workerd, but its stateful connection and its ordered message queue serve editors that send many requests at once; here one Runner request is in flight at a time and order comes from the journal position and the generation. `jayson` and MetaMask's engine import Node built-ins. No library at all would mean rewriting reply matching, timeouts and error replies.
- A full validation layer around the library: its envelope checks are loose, but both ends validate every method with Zod, the mislabels only change an error's text, and the one input that throws, an array, is rejected anyway because one object per message is our profile.
- The hub pushing commands down a stream, with an outbox for what was sent while the Runner was away: a pending answer does not survive hibernation, and the outbox would be a second ordered store next to the journal. A thin hint and a Runner pull need neither; Stripe's thin events and Nomad clients pulling changed allocations by index do the same.
- A revision counter per job: within one placement nothing moves backwards, so the counter would duplicate the generation and the forward-only intents and add one more thing to persist and acknowledge. Withdrawing a pause or raising limits mid-run would need it, and neither exists.
- An alarm per Runner to record liveness: the syncs carry it, and an alarm is one more timer in an object that must hibernate.
- Accepting the socket and then closing it when the version is unsupported: the Runner's client rejects a handshake that selects no subprotocol it offered before it ever sees the close reason, and selecting one we do not support to deliver an error would misstate what was negotiated. Docker's API answers a version out of range with a 400 naming its minimum and maximum.
- Compressing batches ourselves: entries measured on pi's transcripts are around a kilobyte, a batch of ten shrinks to a quarter on the wire, and the extension already does it per connection.
- Sending the root conversation's entries only: a job waiting on a sub-agent would show a tool running for minutes with nothing behind it, and the sub-agent's transcript would be lost.

## Consequences

ADR 0008's paragraph on the oRPC protocol, its subscription, and the alarm is replaced; its addressing, identity and heartbeat stand. ADR 0018's contract package keeps the HTTP contract and gains the socket's method schemas; `@orpc/hibernation` and oRPC's WebSocket handlers and link leave. No Runner is deployed, so nothing migrates. The hub's connection object must stay able to hibernate, so no promise waits for a Runner's answer outside a Workspace read and lint forbids timers in it (ADR 0014). The spec's pause and resume need two rules the protocol exposes: a job resumes only after its pause is confirmed, and a paused job is cancelled before it is deleted; they go to the issues for those stories. Storing pi's entries and conversation records unchanged ties the stored history to pi's shapes, which each job's recorded pi version identifies. Neither hub caps a message itself: Workers drops a received message over its own limit, and the Node hub keeps `ws`'s default; what can grow, a report's entries, is bounded where it is produced. A term for a sub-agent's own transcript is still to be named in the glossary.
