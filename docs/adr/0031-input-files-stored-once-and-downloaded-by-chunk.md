# Input files are stored once by hash and downloaded a chunk at a time

A job's Input files no longer travel in the hub's answers to a Runner (ADR 0026). The hub stores each file's content once, keyed by the SHA-256 of its original bytes, however many jobs use it: a `blob` row with the hash and size, and its bytes in `uploadChunk` rows of a fixed number of original bytes each (the last holds the rest), each compressed as one zstd frame at zstd's default level, as small as gzip's or much smaller for a fraction of its CPU time. The number is recorded with the blob's upload, 1 MiB for what the hub stores now, so the hub can choose another for new blobs without rewriting what it stored. A job's `inputFile` row names its blob by hash. An answer lists each of a job's files by path, digest, size and chunk size, and the Runner downloads it from `GET /jobs/{id}/input-files/{+path}/chunks/{index}`, the path's `/` unencoded, with its own key, one chunk per request, until it has the listed size; it checks the size and SHA-256 and only then moves the file into `inputs/`. It downloads before the job's journal opens, and only when no journal exists, so a resumed or recovered job keeps the agent's edits to its files. A file that cannot be downloaded fails the job with `runFaulted`, naming the file.

The bytes belong to an `upload` row, which the blob is reached through, rather than to the blob itself, so an upload writes its chunks before its content is verified and publishes them without copying (ADR 0035). Deleting a blob deletes its upload and chunks; an `inputFile` row, and a Batch's `batchInputFile` row, keeps its blob (`ON DELETE RESTRICT`). Deleting a job deletes, in the same transaction, the blobs nothing else uses, no other job or Batch and no Organization's upload under seven days old: it locks them before deleting the job and deletes them in a later statement. A submission locks the blobs it names with a key-share lock, in the order of their address as the deletion locks them, so a submission that waits for a deletion finds the blob gone and refuses the file, a deletion that waits for a submission keeps it, and submissions sharing a blob go on together. An upload's publication inserts the blob, or locks the one stored with an update's lock, so it waits for a deletion and stores the blob afresh.

## Considered options

- Content in the answers, as before: an answer carried every placed job's files, so its row passed Node's largest string and the hub's process ended, and an answer over `ws`'s 100 MiB default dropped the Runner's socket on every redial.
- One streamed response per file, the chunks' frames joined: a request's CPU time would grow with the file, where a request per chunk bounds it by one chunk on any plan, as Workers Free's 10 ms per request needs. Node's built-in zstd decoder before 26.10 stops at the end of the first frame of a stream that holds several, or fails when a write holds the end of one frame and the start of the next (checked on 22.19, 22.23, 24.21 and 26.8), and the Runner supports Node 22; a whole frame per response needs no other decoder. And a dropped transfer is retried by the chunk rather than the file. A chunk is answered whole, with its length.
- One `bytea` per file: Postgres rewrites a TOAST value on every append, so a file written in several requests could not grow without rewriting it, and writing it whole needs it in memory.
- Large objects: they append as fast, but a schema-filtered `pg_dump` leaves them out without `-b`, logical replication skips them, they sit outside the `agent_batch` schema (ADR 0014), and each needs `lo_unlink`.
- A copy of the content per job: a batch sharing a file would store and write it once per job.
- Removing unused blobs in the periodic sweep alone: a job's deletion still deletes the content nothing else holds at once, so a deleted job's content outlasts it only while an upload holds it. The sweep (ADR 0035) takes what an upload's expiry leaves unused.
- Hashing the stored zstd bytes: the address would change with the codec or its level, and the Runner could check nothing after decompressing.

## Consequences

A file of _n_ chunks takes _n_ requests, each checking the Runner's key, which Better Auth records by updating the key's row; latency per request is the price of whole frames, and the requests are independent, so a Runner could fetch several at once or resume a download from the first chunk it lacks; today it fetches one at a time and starts a failed file again from the first. A `bytea` crosses from Postgres to node-postgres as hex text, twice its size, so the chunk query selects it as base64, a third larger. Each job downloads its own copy, so a file a batch shares crosses the network once per job. Reconsider the request per chunk once none of its three reasons holds: no hub plan bounds a request's CPU time, the Runner's minimum Node version decodes joined frames, and retrying a whole file costs little.
