# The default environment runs real commands in an OS sandbox per job, through pi-env

> Measurement scope: the figures below record development probes with the stated suite or workload. They are not release benchmarks or guarantees for other versions, hosts or workloads.

A job's commands run as real programs on the host, inside an OS sandbox of the job's own: Anthropic's sandbox-runtime, used as a library in the Runner, which confines processes with bubblewrap and seccomp on Linux and Seatbelt on macOS. The sandbox runs pi-env's daemon (`@earendil-works/pi-env`, from pi-durable's authors), which carries out the job's file operations and runs its commands; the Runner reaches it over the daemon's stdin and stdout through pi-env's `RemoteExecutionEnv`, a complete pi-durable `ExecutionEnv` that its authors test against pi-durable's conformance suite. pi-durable's tools and `submit_result` stay in the Runner, so every file access and every command of a job meets the same rules, enforced by the kernel, and the Runner has no file code of its own. The sandbox can read the host's programs and libraries, and read and write only the job's Workspace and its temp directory beside it: other jobs' files, the Runner's data and the operator's home are not there, and a symbolic link pointing out of the allowed paths resolves to nothing. Commands have no network. Version 1 runs on Linux, on Windows through WSL, and on macOS; where no sandbox can start, the Runner refuses to start unless its operator opts out.

The agent sees the Workspace at its real path: sandbox-runtime cannot remap paths, and Seatbelt has no mount namespace. Temporary files go to the job's temp directory, named in `TMPDIR`, which `mktemp`, Python's `tempfile`, Node's `os.tmpdir()` and GNU `sort` honour, and the agent is told to use it rather than `/tmp`, which inside the sandbox is the job's own but held in memory. sandbox-runtime's write protection for shell and tool settings (`.bashrc`, `.git/hooks` and others) stays on, with `.git/config` writable (`allowGitConfig`); it covers such files only where they exist below the Runner's working directory when a sandbox starts.

Where the host has a user systemd manager, each job's sandbox runs in a systemd scope capped at 1 GiB of memory by default, a Runner setting, with no swap and `OOMPolicy=continue`: the kernel stops the process that went over, the daemon and the job's other processes carry on, and the Runner tells every command that ended meanwhile that a process of the job went over, and what the limit is. Swap stays off because the job survives the stop: with swap, the command would finish more slowly, but its overage would cost the other jobs and the host, as disk I/O they share or as RAM when the swap is zram, and only on hosts that have swap. A runaway command would still be stopped, only later, once swap filled. A job that needs more memory needs a larger cap. Without such a manager (Docker without systemd, macOS) the Runner logs that jobs run uncapped. Files written to the sandbox's `/tmp` count against the cap. The default is a starting limit, not a guarantee that every workload fits; operators can raise it for jobs that need more memory.

Measured on Linux with 100 jobs at once: about 5 MiB of memory per idle job (the daemon 1.35 MiB; the rest bubblewrap, seccomp helpers, wrapper shells and sandbox-runtime's two network relays), a command in about 2 ms and a file operation in about 0.1 ms. Real tools are leaner and faster than just-bash's: on a 9.5 MB file, `sort` took 46 MiB and 0.16 s against about 470 MiB and 1.1 s, `sed` 0.13 s against 4.4 s, and under a 128 MiB heap just-bash's `sort`, `sed`, `tr` and `base64` ran out of memory on that file. just-bash's memory advantage came from many jobs sharing one process, and its synchronous commands block whatever process they share, so in its own process per job it cost 26–60 MiB per idle job.

## Considered options

- just-bash on a real directory in a shell process per job, under Node's permission model: 26–60 MiB per idle job, far more time and memory per command on real data, commands that cannot be stopped from inside the process, and a permission model documented as a guard against mistakes that follows symbolic links out and leaves the network open below Node 26.
- A sandbox per command, with the file tools in the Runner confined by path checks (just-bash's `ReadWriteFs` or our own): a second set of rules that must match the sandbox's (its write protection, the temp directory, symbolic links), checked between resolving a path and opening it, which Node cannot do in one step, and file work on the Runner's thread.
- A sandboxed Node process per file-tool call running pi-durable's tools: about 200 ms and 28 MiB per call, most of it starting Node and loading the tools.
- OpenSSH's `sftp-server` in each job's sandbox, with a sandbox per command: 0.12 MiB per server and tested, but it needs our own `ExecutionEnv` over SFTP, built on an internal class of ssh2's, reports failures with SFTP's few status codes, and spends 7–30 ms per command plus 6–8 ms of the Runner's thread wrapping it. It is the fallback if pi-env falls short.
- A sandbox launcher of our own around bubblewrap and Seatbelt: sandbox-runtime is maintained for Claude Code on both, and supports network filtering.
- A container or micro-VM per job: adds a separate runtime and lifecycle for every job.
- A memory cap per command: a job's commands run in its long-lived sandbox, so the cap is the job's.

## Consequences

Python, Node, SQLite and the rest are whatever the host has.

A Linux host needs `bwrap`, `socat` and `rg` on its `PATH`, sandbox-runtime's dependencies, and on Ubuntu 24.04 `kernel.apparmor_restrict_unprivileged_userns=0`, since AppArmor strips the capabilities from the user namespaces that bubblewrap and sandbox-runtime's seccomp helper create. Ubuntu 25.04 and later deny capabilities to everything bubblewrap starts, the helper included, whatever the sysctl, so jobs cannot run in a sandbox there until anthropics/sandbox-runtime#429 is fixed. Docker's default seccomp and AppArmor profiles prevent bubblewrap inside a container, and Docker masks paths under `/proc`, so a sandbox cannot mount its own; the Runner's image runs as a non-root user with `seccomp=unconfined`, `systempaths=unconfined` and, on hosts with AppArmor, `apparmor=unconfined`, with `kernel.apparmor_restrict_unprivileged_userns=0` on Ubuntu 24.04, as BuildKit's rootless image does. A container has no user systemd, so there the container's memory limit caps the Runner and its jobs together. pi-env ships its daemon as a binary for each platform in its npm package. A job's commands share its sandbox: what they leave running lives until the job ends, when the Runner stops the daemon and the daemon stops everything it started. Native Windows waits until a sandbox there can give each job its own Workspace. pi-durable's tools still run in the Runner, so their own work, such as the display diffs `edit` computes, still runs on its thread; for realistic edits that stays under 100 ms.
